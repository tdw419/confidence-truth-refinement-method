Abstract
--------

This document presents a novel approach to codebase organization called "Physical Truth Management" that uses git history as a truth database and filesystem structure as a spatial truth map. The system addresses the growing complexity of AI projects by organizing code based on its actual importance rather than arbitrary structure.

The Core Problem
---------------

AI projects become too complex over time because there's no stable reference point. Developers struggle with:

1. **Complexity Overload**: As projects grow, finding important code becomes difficult
2. **Truth Decay**: No objective way to determine which code is reliable
3. **Structural Rigidity**: Traditional directory structures don't reflect actual usage
4. **Maintenance Burden**: Identifying technical debt is subjective and time-consuming

The Key Insight
--------------

Git already tracks what matters: change, stability, and usage. The filesystem should reflect code's actual importance.

Core Principles
--------------

1. **Truth as Architecture**: Organize code by veracity, not just structure
2. **Git as Oracle**: Use history to reveal what's actually important
3. **Physical Proximity**: Important code lives near the root (easy to find)
4. **Self-Cleaning**: Bad code naturally gets pushed away from center
5. **Objective Metrics**: No guessing - git tells us what matters

The Physical Truth Management System
------------------------------------

### Filesystem as Spatial Map

- **Root directory = Center of truth**: Most important code at distance 0
- **Directory depth = Distance**: Deeper nesting = less critical
- **Physical proximity = Cognitive proximity**: Important code is easy to find

### Git as Truth Database

No separate metadata needed - git already tracks everything:

- `git grep` → import frequency (usage)
- `git log` → commit history and stability
- `git log --diff-filter=A` → file age
- `git shortlog -sn` → contributor count
- `git log --numstat` → lines changed

### Truth Scoring Algorithm

```
truth_score = (
    0.40 * normalize(import_count) +
    0.30 * normalize(stability) +
    0.20 * normalize(age) +
    0.10 * normalize(contributors)
)
```

### Distance Recommendations

| Distance | Status        | Truth Score | Imports | Description                    |
|----------|---------------|-------------|---------|--------------------------------|
| 0        | Foundational  | ≥0.90       | ≥100    | Root level - core utilities    |
| 1        | Core          | ≥0.80       | ≥50     | Essential shared code          |
| 2        | Stable        | ≥0.70       | ≥10     | Reliable services              |
| 3        | Working       | ≥0.60       | Any     | Active development             |
| 4        | Experimental  | ≥0.45       | Any     | Unproven features              |
| 5+       | Review        | <0.45       | Any     | Needs review or archival       |

Implementation Requirements
---------------------------

### Core Components

1. **Git Metrics Analyzer**
   - Extracts truth metrics from git history
   - Calculates import counts, commit frequency, file age, contributors
   - Works with any git repository

2. **Truth Score Calculator**
   - Implements weighted scoring formula
   - Recommends optimal distance from repository root
   - Categorizes files by status

3. **Truth Manifest Storage**
   - SQLite database for fast queries and history tracking
   - JSON export for human-readable snapshots
   - Tracks changes over time

4. **CLI Interface**
   - `analyze` - Full repository analysis
   - `rank` - Truth ranking for specific file
   - `list` - Filter by status
   - `export` - Generate JSON reports
   - `set` - Manual overrides

Expected Benefits
----------------

1. **Reduced Complexity**: Important code is always easy to find
2. **Objective Truth**: No more guessing about code quality
3. **Self-Organizing**: System reflects reality over time
4. **Better Maintenance**: Technical debt is automatically identified
5. **Improved Onboarding**: New developers find important code faster

Success Criteria
---------------

The system is working if:

✅ Files with high import counts get high scores
✅ Stable, old files get higher scores than new, churning files
✅ Promotion/demotion suggestions make intuitive sense
✅ Foundational code is identifiable
✅ Low-value code is flagged for review

Conclusion
----------

This system makes the key insight actionable: organize code by its actual importance, not arbitrary structure. By using git as a truth database and the filesystem as a spatial map, we create a self-organizing system that naturally reflects code's true value.

The Physical Truth Management System provides an objective, data-driven approach to codebase organization that scales with project complexity and helps maintain code quality over time.
